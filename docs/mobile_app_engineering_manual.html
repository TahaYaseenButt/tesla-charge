1.0 Architecture Overview & State Pipeline

The Tesla Charge mobile application delivers real-time monitoring and control for DC Fast EV Charging stations. In the current standalone architecture, the application communicates directly with the self-hosted T-Charge server (https://tesla-charge.online) via lightweight HTTP REST endpoints and local state subscriptions, bypassing heavy third-party Firebase SDKs.

Figure 1.1: Mobile Application Architecture, State Flow, and Telemetry Engine

1.1 Zero-Latency Initial Render (0ms Cache Pattern)

When the driver opens the app, waiting for a network roundtrip introduces layout shifting and perceived sluggishness. useChargerLive implements a two-tier fetch:

  1. Tier 1 (Synchronous Cache, 0ms): Reads previous session telemetry, connector statuses, and charger metadata from local AsyncStorage. The UI immediately renders the station and last-known gun states without a loading spinner.
  2. Tier 2 (Live Network Stream, 2.5s Polling): Connects via subscribeToLiveStatus to fetch real-time SoC, kW, voltage, and transaction state directly from the server. Upon receipt, local cache is silently refreshed.

3.0 In-App Telemetry & Notification Engine

One of the most critical user experience requirements is instantaneous notification when a physical charging cable is plugged into a vehicle. The mobile application employs a dual-channel notification strategy:

Figure 3.1: In-App Plug-In Transition Detection and Immediate Notification Flow

3.1 State Tracking Implementation in index.tsx

const prevStatus1Ref = useRef<string | null>(null);
const prevStatus2Ref = useRef<string | null>(null);

useEffect(() => {
  const status1 = connector1?.status;
  if (status1 && prevStatus1Ref.current && prevStatus1Ref.current !== status1) {
    if (status1 === 'Preparing') {
      scheduleLocalNotification(
        '⚡ Vehicle Connected to Gun A!',
        'Gun A is plugged into your vehicle. Tap here to start charging.',
        { gun: 'A', connectorId: 1 }
      );
    } else if (status1 === 'Charging') {
      scheduleLocalNotification('⚡ Gun A Charging Started', 'Power is now flowing to your vehicle.');
    }
  }
  prevStatus1Ref.current = status1 || null;
}, [connector1?.status]);

4.0 Built-In Desk Simulator Architecture

To enable mobile engineers to build, refine, and debug UI layouts, charging animations, and session receipts without access to a physical 240kW DC fast charging station, the application includes a full-fidelity embedded simulator (src/components/SimulatorModal.tsx and src/config/simulator.tsx).

4.1 Simulator Capabilities

  • Independent Gun Simulation: Toggle Gun A or Gun B between Available, Preparing, Charging, and Faulted states.
  • Real-Time Power & Meter Progression: Simulates realistic DC charging curves from 20kW up to 240kW, automatically advancing delivered energy (kWh), elapsed time, and State of Charge (SoC %).
  • Limit Trigger Testing: Simulates automatic session completion when budget (PKR) or kWh limits are reached.
  • Zero Server Pollution: All simulator calculations execute in React memory; no test transactions are sent to the production SQLite database.

5.0 EAS Build, Release & OTA Update Pipeline

The application leverages Expo Application Services (EAS) for both binary compilation and instantaneous Over-The-Air (OTA) updates. This allows engineering to push bug fixes and feature enhancements directly to driver phones without submitting new APKs to store review.

5.1 EAS Configuration Matrix (eas.json)

5.2 Publishing Over-The-Air (OTA) Updates

Because app.json defines runtimeVersion: "1.0.0", any JavaScript, TypeScript, or asset changes can be deployed in under 60 seconds using the following command: 

# From production/mobile-app directory:
npx eas-cli update --channel preview --environment preview --message "feat: live telemetry updates" --non-interactive
Runtime Version Boundary: OTA updates apply only to JavaScript bundle and asset updates. If a new native library is added (e.g., changes to android/ or native dependencies in package.json), a full binary build must be compiled using eas build --platform android --profile preview.

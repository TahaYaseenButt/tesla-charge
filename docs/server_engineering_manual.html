1.0 Architectural Overview & System Topology

The Tesla Charge server is a high-reliability, self-hosted Electric Vehicle Supply Equipment (EVSE) management system engineered specifically for DC Fast Chargers (e.g., 240kW dual-gun and 30kW single-gun stations). Historically, telemetry and commands relied on an external Firebase Realtime Database. The current production release eliminates all external cloud runtime dependencies, replacing them with a local, zero-latency SQLite architecture with WAL (Write-Ahead Logging) concurrency.

Figure 1.1: Complete End-to-End System Topology and Component Interaction

1.1 Design Specifications & Target Capacity

  • User Envelope: Engineered for up to 100 registered drivers with 10 concurrent active charging and telemetry sessions without performance degradation.
  • Compute & Memory Footprint: ~55 MB Resident Set Size (RSS) memory consumption on standard Linux / macOS kernels. Runs comfortably on a Raspberry Pi 4 or 1 vCPU cloud instance.
  • Dual Protocol Exposure: Runs HTTP/REST and WebSocket listeners concurrently on the same port (default: 3000, with reverse-proxy support on 443/8887).
  • Zero External Cloud Dependency: Fully operational during internet backhaul degradation for local LAN charging stations.

3.0 Database Schema & Concurrency Architecture

The database engine is better-sqlite3, running synchronously in the Node.js event loop with direct C++ V8 bindings. Because Write-Ahead Logging (WAL) is enabled, readers never block writers, and writers never block readers. This guarantees sub-millisecond query response times for mobile app polling while OCPP telemetry messages stream in from physical chargers.

3.1 Entity Relationship Details

Engineers' Note on WAL Mode Maintenance: SQLite manages tcharge.db-wal and tcharge.db-shm files automatically during runtime. When taking hot backups, use the SQLite Online Backup API or copy the files when the server process is stopped. Do not delete .db-wal or .db-shm while the process is active!

4.0 OCPP 1.6-J State Machine & Protocol Flow

The server implements the OCPP 1.6 JSON specification over WebSockets (RFC 6455). Communication uses JSON-RPC framing: [MessageTypeId, UniqueId, Action, Payload] for Calls (Type 2), and [MessageTypeId, UniqueId, Payload] for CallResults (Type 3).

4.1 Predictive Latency Compensation Algorithm

When a driver sets a target limit (e.g., PKR 1,000 or 15.0 kWh), stopping the session exactly when the meter value crosses the threshold results in substantial over-billing due to hardware communication latency (typically 3 to 8 seconds). The server implements predictive lead-time math in actionHandlers.js: 

const leadSeconds = 5;
const projectedKwhLead = kw > 0 ? (kw * (leadSeconds / 3600)) : 0;
const projectedCostLead = projectedKwhLead * tariff;

if ((liveCost + projectedCostLead) >= targetPrice) {
  shouldStop = true;
  stopReason = `Predictive budget limit reached: PKR ${liveCost} (+PKR ${projectedCostLead.toFixed(1)} projected @ ${kw.toFixed(1)}kW) >= target PKR ${targetPrice}`;
}

5.2 Command Dispatch Request / Response Normalization

To ensure backwards compatibility with diverse mobile client versions, POST /api/commands/dispatch automatically normalizes payloads:

  • Supports top-level action or nested command.
  • Unpacks parameters: { connectorId, idTag } to top-level fields automatically.
  • Returns dual aliases: result and response, plus reason and stopReason.

6.0 Deployment & Operations Runbook

6.1 System Prerequisites

  • Node.js v18.16.0 or higher (ES Modules required).
  • Linux Kernel 5.4+ or macOS 12+ (supports POSIX file locks for SQLite WAL).
  • Open Ports: 3000 (HTTP/REST & WebSocket), or 8887 / 443 if configured via reverse proxy.

6.2 Environment Variables (.env)

PORT=3000
JWT_SECRET=production-crypto-key-replace-with-64-char-random-hex
DEFAULT_TARIFF_RATE=125.0
DEFAULT_CURRENCY=PKR
ENABLE_CLOUD_MIRROR=false

6.3 Starting the Server in Production

Option A: Native Node.js / Systemd Daemon

# 1. Install dependencies
npm ci --only=production

# 2. Start standalone server
node src/index.js

# 3. For systemd management:
sudo cp tcharge-server.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now tcharge-server
sudo systemctl status tcharge-server

Option B: Docker Compose Containerization

# Build and start container in detached mode with persistent volume
docker compose up -d --build

# View real-time logs
docker compose logs -f

6.4 Reverse Proxy Configuration (Nginx WebSocket Example)

server {
    server_name tesla-charge.online;

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_read_timeout 300s;
        proxy_send_timeout 300s;
    }
}
